1. Architecture Findings

Full inspection of V1–V17 Flyway migrations, all repositories, services, controllers, routes, middleware, and frontend pages was performed before writing a single line of code.

  • Teachers table: had no mobile_number column — added in V18.
  • Classroom model: single teacher_id FK on classrooms — preserved as-is.
  • Teacher/classroom assignment: teacher registers first → admin assigns classroom (safer architecture, preserves existing FK constraint).
  • Registration codes: no existing table — new teacher_registration_codes table added in V18.
  • Security pattern: all tokens use SHA-256 hash storage (token.util.js) — registration codes follow the same pattern.
  • Rate limiting: reused existing registerLimiter for teacher registration endpoint.
  • Email verification: teacher registration fires the existing issueEmailVerificationToken flow (same as admin-created teachers).

3. New Migration

V18__teacher_registration_codes.sql
  
  ALTER TABLE teachers
    ADD COLUMN mobile_number VARCHAR(20) NULL DEFAULT NULL;
  
  CREATE UNIQUE INDEX uq_teachers_mobile_number ON teachers (mobile_number)
    WHERE mobile_number IS NOT NULL;
  
  CREATE TABLE teacher_registration_codes (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code_hash   CHAR(64)  NOT NULL,  -- SHA-256 only; raw never stored
    created_by  INTEGER   NOT NULL,  -- admins.id
    expires_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    used_at     TIMESTAMP WITH TIME ZONE NULL DEFAULT NULL,
    used_by     INTEGER   NULL DEFAULT NULL,
    is_revoked  BOOLEAN   NOT NULL DEFAULT FALSE,
    created_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_teacher_reg_code_hash UNIQUE (code_hash),
    CONSTRAINT fk_teacher_reg_code_admin FOREIGN KEY (created_by) REFERENCES admins(id)
  );

7. Teacher Registration Flow

ADMIN: POST /admin/teacher-registration-codes
↓
Server generates 8-char code (cryptographically random, unambiguous charset)
↓
SHA-256 hash stored in teacher_registration_codes.code_hash
↓
Raw code returned ONCE in format "ABCD-1234" (never stored or returned again)
↓
Admin shares code with teacher out-of-band
↓
TEACHER: opens /register/teacher, fills form + teacher code
↓
POST /auth/teacher/register → Joi validation → service layer
↓
hashToken(code) → findValidByHash() — checks not expired, not revoked, not used
↓
existsByEmail / existsByMobile duplicate checks
↓
bcrypt.hash(password) → teacherRepo.create() — role ALWAYS = teacher (server-enforced)
↓
teacherRegCodeRepo.markUsed(codeId, teacherId) — code consumed
↓
audit_logs: teacher_self_registered
↓
issueEmailVerificationToken() fire-and-forget
↓
issueTokenPair() → 201 {accessToken, refreshToken, permissions, user}
↓
Teacher can now login; admin assigns classroom via PATCH /admin/teachers/:id/classroom

8. Admin Teacher-Management Flow

  • Generate code: POST /admin/teacher-registration-codes — gets display code once
  • List codes: GET /admin/teacher-registration-codes — status/expiry/used-by; hash never returned
  • Revoke code: POST /admin/teacher-registration-codes/:id/revoke — idempotency checks
  • List teachers: GET /admin/teachers — password_hash, failed_login_attempts, locked_until stripped
  • View teacher: GET /admin/teachers/:id — includes classrooms array, no sensitive fields
  • Update teacher: PATCH /admin/teachers/:id — name/email/mobile with conflict checks
  • Activate/deactivate: PATCH /admin/teachers/:id/status with {isActive: bool}
  • Assign classroom: PATCH /admin/teachers/:id/classroom with {classroomId}
  • Remove from classroom: DELETE /admin/teachers/:id/classroom/:classroomId
  • Every action writes an audit_logs row with actor/target/action

9. Teacher / Classroom Assignment Model

Architecture: Teacher registers → Admin assigns classroom.

The existing schema has a single teacher_id FK on classrooms. This constraint is preserved. Teachers self-register without being pre-assigned to a classroom. After registration, an admin uses PATCH /admin/teachers/:id/classroom to set the classroom's teacher_id. "Remove from classroom" deactivates the classroom (since the NOT NULL FK cannot be set to NULL) and the admin must reassign to reactivate.

10. Security Measures

  • Registration code hashing: only SHA-256 hash stored; raw code shown once, never recoverable from DB
  • Role enforcement: role is always 'teacher' — set server-side, client cannot submit it
  • Generic error messages: invalid code / expired / revoked / used all return the same 400 message; email/mobile conflicts return the same 409 message (no enumeration)
  • No sensitive fields in responses: password_hash, failed_login_attempts, locked_until stripped from all list/detail responses
  • Rate limiting: registerLimiter (8 attempts / hour) applied to teacher registration endpoint
  • Admin-only enforcement: all code management and teacher management endpoints gated by authenticate + authorizeRoles('admin')
  • Audit logging: code created/revoked, teacher registered/updated/activated/deactivated/assigned/removed all logged — raw code and password_hash never logged
  • Email verification: teacher registration follows same REQUIRE_EMAIL_VERIFICATION flag as admin-created teachers
  • Single-use codes: code consumed on first successful registration via markUsed(); subsequent attempts find no valid record
  • Expiry: expires_at checked in findValidByHash() SQL query; default 24h, configurable per code
  • Revocable: is_revoked flag, checked in same query
  • Crypto: code generated with crypto.randomInt(), token with crypto.randomBytes() — no Math.random()
