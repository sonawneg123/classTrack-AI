2. DATABASE CHANGES
--------------------------------------------------------------------------------

(classTrackv1-backend/database/migrations/flyway/V19__profile_photos.sql)

  ALTER TABLE admins
    ADD COLUMN IF NOT EXISTS avatar_path VARCHAR(500) NULL DEFAULT NULL;

  ALTER TABLE teachers
    ADD COLUMN IF NOT EXISTS avatar_path VARCHAR(500) NULL DEFAULT NULL;

  ALTER TABLE students
    ADD COLUMN IF NOT EXISTS avatar_path VARCHAR(500) NULL DEFAULT NULL;

Design decisions:
  - avatar_path stores a relative filesystem path
    e.g. "uploads/avatars/1719830412345-f4a8b2c1…d9.jpg"
  - NULL = no photo set → frontend falls back to initials
  - No separate profile table created — column lives on the account row
  - Forward-only, idempotent (IF NOT EXISTS), PostgreSQL 16 compatible
  - No existing migration was modified
  - Easy S3 migration: avatar_path becomes an object key;
    buildAvatarUrl() returns a CDN URL instead of the local API path


--------------------------------------------------------------------------------
3. STORAGE ARCHITECTURE
--------------------------------------------------------------------------------

  Database:  Stores relative path reference only. No binary data in DB.
  Disk:      Files stored under uploads/avatars/ (configurable).
  Filename:  Server-generated: {timestamp}-{16-byte-crypto-hex}.{ext}
             Original filename NEVER used (path traversal prevention).
  URL:       /api/v1/account/avatar/:filename  (public, 7-day cache header)
  Cleanup:   Old file deleted best-effort after DB update succeeds.
             Failure is logged; never blocks the HTTP response.
  S3 path:   Replace _deleteAvatarFile() with S3 deleteObject.
             Replace buildAvatarUrl() to return CDN URL.
             No schema change required.

4. API ENDPOINTS IMPLEMENTED
--------------------------------------------------------------------------------

  GET    /api/v1/account/profile
         Auth: Required (Bearer token)
         Returns current user full profile including avatarUrl.
         Works for admin, teacher, student.

  PUT    /api/v1/account/profile/photo
         Auth: Required (Bearer token)
         Body: multipart/form-data, field name: "photo"
         Accepts: image/jpeg, image/jpg, image/png, image/webp (max 5 MB)
         Uploads or replaces the profile photo.
         Returns updated profile with new avatarUrl.

  DELETE /api/v1/account/profile/photo
         Auth: Required (Bearer token)
         Removes profile photo. Returns updated profile (avatarUrl: null).
         Idempotent — safe to call even when no photo is set.

  GET    /api/v1/account/avatar/:filename
         Auth: NOT required (public)
         Serves stored avatar image file.
         Returns 404 for missing files.
         Rejects path-traversal attempts.
         Cache-Control: public, max-age=604800, immutable

  GET    /api/v1/auth/me  (MODIFIED — was already existing)
         Auth: Required (Bearer token)
         Now includes profile.avatarUrl in response.
         Used by AuthProvider on every session bootstrap and login.

7. SECURITY MEASURES
--------------------------------------------------------------------------------

Upload:
  - MIME type allowlist: image/jpeg, image/jpg, image/png, image/webp only
  - SVG explicitly rejected (not in allowlist — XSS risk)
  - Arbitrary file types rejected by multer fileFilter
  - Executable/binary uploads rejected
  - Max size: 5 MB (frontend + backend both enforce)
  - Magic-byte (file signature) verification post-upload
    JPEG: 0xFF 0xD8 0xFF
    PNG:  0x89 0x50 0x4E 0x47
    WebP: RIFF....WEBP

Filename:
  - Never uses original filename from client
  - Server generates: {timestamp}-{crypto.randomBytes(16).toString('hex')}.{ext}
  - Extension sanitized: /[^a-z.]/g stripped

Serving:
  - path.basename() strips all directory components
  - Resolved path must start with AVATAR_UPLOAD_DIR + sep
  - Path traversal sequences rejected with 404

Authorization:
  - userId always from req.user (JWT payload) — never from request body
  - Cross-user modification impossible by design
  - /auth/me re-checks is_active + locked_until on every request

Logging:
  - File contents never logged
  - Only logs: userId, role, basename of filename (not full path)
  - No sensitive user data logged unnecessarily

Responses:
  - API never returns filesystem paths
  - API never returns auth secrets or credentials
  - Stack traces never returned to frontend

8. CACHE / UI SYNCHRONIZATION
--------------------------------------------------------------------------------

After upload or delete:
  Step 1: queryClient.setQueryData(PROFILE_QUERY_KEY, freshProfile)
          → Profile page updates immediately with server-confirmed data

  Step 2: refreshUser() called on AuthProvider
          → Re-fetches GET /api/v1/auth/me
          → setUser(currentUser) updates React context
          → ProfileMenu (Topbar) avatar updates WITHOUT page refresh

Avatar URL cache-busting:
  → Each upload generates a new random filename
  → Browser Cache-Control: public, max-age=604800, immutable
  → Because filename changes on every upload, stale avatar caching is
    impossible even with long cache TTLs
